## 解释与待评估事项

HTTPS small warm 的 008 三轮 nominal RPS 分别为 11147.63、11348.03、10740.00，current 为 10161.93、9994.97、11705.93；两者中位数差 -8.84%，六轮均有客户端受限警告。current 第三轮高于 008 全部三轮，但不能因此抹去中位数退化，也不能推断其原因。建议后续评估是否交错顺序重复测量并改进采样；本次未额外运行 full。

CPU 数字保留原始 sampled peak，不删样本或静默截断。记录中 client 峰值达到 960.829% 和 941.73%，但 client 限定两个 CPU 且为单 PID，超过理论上限。静态检查 frozen `metrics.py` 的 sample 使用 tick_delta/(now-last)，runner 的 sampled 先 sample 再创建 sampler.run 任务，后者立即再次 sample；短间隔 tick 量化可能造成虚高。这只是静态机制解释，不是动态 profile 或因果证明。独核只确认 raw 峰值计算一致，未证明实际 CPU ticks 或内核数据；平均 CPU 未测量，不能从这些峰值作硬件或真实性能结论。未安装 perf，也不据此优化产品。

本次差异调查按已保存的逐轮分布、闭环请求窗口及资源采样边界进行，未新增性能剖析或额外测量。HTTPS small warm 的吞吐及尾延迟退化如上保留；HTTPS small cold 的 p95/p99 增加 10.3%/11.1%，同时吞吐下降 3.1%，仍无法从本轮固定顺序和受限客户端数据定位服务器内因。其余 HTTP 场景的吞吐下降在 1.7% 以内，两个 HTTPS large 场景吞吐分别增加 9.2%/11.8%，不能据此抵消小文件退化或推广为普遍提升。RSS 各场景增加约 16.2%–19.9%，绝对值约增加 3–4 MiB；idle 的线程中位数从 4 增至 7、FD 从 15 增至 19。这些是默认观测关闭时仍存在的真实进程资源差异，不能称默认零开销；既有观测 owner 即使关闭也会预建后台线程，但该静态事实不足以量化分摊全部 RSS 或归因吞吐差异。CPU sampled peak 的采样缺陷使其不适合因果调查，原数值及限制均保留。5% 若用于筛选仅为描述，不是项目确认的门禁阈值或失败判定。闭环并发、客户端受限警告和固定目标顺序限制解释，但不能抹去已测退化，也不能据此证明原因。没有 perf profile，不作无依据的源码优化或容量、饱和、99.9% 可用性结论。请父任务结合上表绝对值与百分比评估 AC02。
